# 성능 개선 2 — 현재 물체 묶음 검사

2026-09-06. 이번 단계는 같은 촬영 장면의 물체를 최대 4개씩 검사하는 실행 경로다. VLM과 GPU 정상 기준 상주는 변경하지 않았다.

## 운영 동작

- 검사 파이프라인은 현재 검출된 물체를 최대 4개씩 처리한다. 9개면 4+4+1이며 다음 프레임이나 추가 물체를 기다리지 않는다. 기준 비교용 API에서는 `inspection_batch_size=1`을 지정할 수 있다.
- 알려진 불량 RF-DETR와 정상 특징 DINO에 `inspect_many`/`predict_many_rgb`/`extract_many`를 연결했다. 형상 등 묶음 API가 없는 검사기는 개별 호출한다. 각 물체의 검사 종류와 필수 항목은 유지한다.
- 추적된 기존 물체는 선택 검사 래퍼에서 제외한다. 새 물체와 재검사 대상만 실제 검사기에 전달한다. 반환 결과의 개수, 순서, 촬영 ID, 물체 ID, 검사 종류, 모델 식별값을 검사한 뒤 원본 좌표로 연결한다. 묶음의 식별값이나 개수가 잘못되면 묶음 결과를 ERROR로 처리하며 누락 결과를 정상으로 채우지 않는다.
- 파이프라인은 한 묶음의 crop만 보유한다. 검사 결과 원본과 기존 비동기 저장/DB 공개/로봇 연계 규칙은 유지한다. `inspection_batches`에 공통 실행 시간을 기록하며, 묶음 검사 항목의 `elapsed_ms`는 같은 호출의 소요 시간이다. 이를 물체별로 더해 전체 시간을 추정하지 않는다.
- RF-DETR은 준비 단계에서 배치 1/2/4용 FP32 JIT를 생성하고 각각의 실행 상태를 보관한다. 불량 검사 대상 3개는 2+1로 실행한다. 패딩용 가짜 물체를 넣거나 프레임마다 재컴파일하지 않는다. 전체 장면 물체 검출기는 배치 1을 유지한다.
- RF-DETR 1.9.4 내부 wrapper/context를 얕게 복사해 원래 가중치를 공유하고, 공식 `inference`가 만드는 실행 사본을 분리한다. 다른 라이브러리 버전에는 이 경로를 자동 적용하지 않는다. 준비 실패나 메모리 부족은 오류로 처리하고 조용히 검사 항목을 생략하지 않는다.
- DINO는 원래 FP32, 이미지 크기, 정규화, 패치와 거리 계산을 유지한다. 이번 단계에서도 특징을 CPU로 돌려받고 정상 기준을 반복 전송한다. 이 전송 개선은 **다음 단계**다.

## 판정 기준과 이전 자료

새 CUDA 불량 모델 식별값은 `1.9.4+fp32_jit+batch4`이며 배치 1 모델의 기존 판정 기준과 다르다. 품목 판정 기준 생성도 공통 모델 식별 함수를 사용한다. 기존 기준을 자동으로 바꿔 승인하지 않는다. 실제 제품 학습과 배치 실행 검증 후 기준을 새로 등록한다.

새 CUDA 정상 특징 기준에는 `feature_signature.batch_limit=4`가 들어가므로 기준 뱅크 해시에도 반영된다. 기존 뱅크는 저장된 batch_limit을 읽으며, 필드가 없으면 1로 실행해 이전 특징 서명과의 호환성을 유지한다. 기존 뱅크를 조용히 묶음 추론으로 바꾸지 않는다. 새 뱅크 구성 시 묶음 지원 서명을 사용하고 제품별 임계값을 검증해야 한다. CPU 기본 특징 추출은 1개씩이다.

## 첫 GPU 측정

RTX 3090 / Windows / PyTorch 2.9.1+cu128 / RF-DETR 1.9.4. 앞 단계 공개 예제 사진을 크기·밝기·반전으로 변형한 crop을 사용했다. 실제 RF-DETR 2개와 DINO 모델, 임의 정상 특징 2,048벡터로 실행했다. 제품 가중치나 실물 정답 데이터가 아니다.

아래는 전체 장면 검출 1회 + N개 crop의 RF-DETR/DINO/기존 거리 계산 소요 시간이다. 전처리와 GPU 완료 동기화를 포함하며, 촬영·안정화·저장·DB·UI·VLM·로봇은 제외한다. 지난 단계의 단일 검출 시간과는 다른 범위다. 비교할 각 조건을 무작위 순서로 섞어 12회씩 측정했다(5개 물체 수 × 3개 묶음 설정 × 12회 = 180표본).

| 현재 물체 수 | 1개씩 중앙값 | 최대 2개씩 중앙값 | 최대 4개씩 중앙값 | 1개씩 p95 | 최대 4개씩 p95 |
|---|---:|---:|---:|---:|---:|
| 1 | 75.06ms | 74.25ms | 73.80ms | 82.27ms | 79.23ms |
| 2 | 131.16ms | 99.70ms | 101.71ms | 141.99ms | 105.50ms |
| 3 | 179.97ms | 156.36ms | 144.42ms | 215.50ms | 154.37ms |
| 4 | 233.49ms | 181.58ms | 154.76ms | 243.19ms | 173.46ms |
| 8 | 451.46ms | 347.87ms | 299.16ms | 463.17ms | 308.39ms |

4개·8개에서 약 34% 감소했다. 물체 1개는 실제로 동일한 배치 1 경로이므로 작은 시간 차이를 배치 개선으로 주장하지 않는다. 이 비교에서는 모든 후보가 같은 상주 모델들을 사용한다. batch2/4 실행 사본을 유지하기 위한 추가 메모리가 필요하며, 준비 후 전체 모델 상주 PyTorch 할당은 약 862.75MiB, 추론 피크는 약 965.21MiB였다. 이는 GPU 전체 사용량이나 단일 모델 측정이 아니다. 최초 적재/컴파일/워밍업 합계는 34.59초였다.

첫 8개 입력의 출력 비교에서 0.4/0.7 점수 이상은 양쪽 8개 모두 대응했고, 최대 좌표 차이 0.01554px, 점수 차이 0.000519였다. 0.05 이상도 양쪽 30개가 모두 대응했으나 좌표 최대 차이는 0.05664px였다. DINO 특징과 거리 결과의 최대 차이는 이 입력에서는 0이었다. 일반적인 완전 동일성이나 제품 불량 정확도를 보장하는 결과는 아니다.

## 실제 프로젝트 반영 후 최종 검증

같은 측정 조건으로 실제 프로젝트 소스에서 180표본을 다시 수집했다. 아래는 중앙값이다. 첫 측정과 최종 측정 간 시간 차이는 실행 환경 변동을 포함하므로, 개선율은 각 실행 안의 순차/묶음 조건으로 비교한다.

| 현재 물체 수 | 1개씩 | 최대 2개씩 | 최대 4개씩 | 1개씩 p95 | 최대 4개씩 p95 |
|---|---:|---:|---:|---:|---:|
| 1 | 67.52ms | 67.89ms | 66.65ms | 82.29ms | 72.94ms |
| 2 | 111.89ms | 89.74ms | 88.99ms | 127.16ms | 96.91ms |
| 3 | 159.64ms | 136.75ms | 125.08ms | 172.91ms | 131.74ms |
| 4 | 205.09ms | 160.59ms | 141.20ms | 255.48ms | 148.18ms |
| 8 | 398.17ms | 308.69ms | 266.28ms | 441.15ms | 307.61ms |

4개는 약 31%, 8개는 약 33% 소요 시간이 감소했다. 준비 시간은 26.97초, 상주 할당/추론 피크는 862.75/965.21MiB였다. 준비한 배치 1/2/4가 검사 중 다시 컴파일되지 않음을 확인했다. 최종 측정에서도 DINO 특징과 최근접 거리의 최대 차이는 해당 입력에서 0이었다. 원시 180표본은 `artifacts/inference-optimization/step2/deployed-gpu/samples.csv`, 상세 결과는 같은 폴더의 `report.json`에 있다.

실제 프로젝트 전체 **393개 시험 통과(53.150초)**. 별도의 연속 통합 검증은 64.53초 동안 1,276프레임을 공급하고 13회 시나리오에서 새 물체 39건 + 재검사 13건 = 52개 결과를 정확히 공개했다. 모델 적재는 1회였으며 추적·중단/재개·재검사·비동기 저장·DB 검증을 통과했다. 이 연속 검증은 카메라와 모델 출력을 주입했으므로 실제 GPU 처리율이나 현장 정확도 측정이 아니다. 약 1분 관측으로 장시간 무누수를 판단하지 않는다.

## 검증 및 다음 작업

- 물체 ID/순서/좌표 연결, 4개 상한·잔여 1개 즉시 처리, 재검사 대상 선별, 잘못된 출력 개수/중복/이전 촬영/예외 차단 시험.
- DINO 물체별 특징·점수·영역/최근접 근거 유지, 기존 뱅크 설정 유지, 실제 합성 학습 가중치의 클래스와 배치 출력 확인.
- 전체 회귀 시험 및 카메라/모델 출력을 명시적으로 주입한 연속 추적·비동기 저장·재검사 시험.
- 실제 소스 GPU 재측정과 원시 기록은 `artifacts/inference-optimization/step2`에 보존한다. `scripts/benchmark_inspection_batches.py`는 사용자가 지정한 로컬 예제 이미지로 재실행할 수 있다. 운영 DB에 검사 결과를 등록하거나 장치에 연결하지 않는다.

실물 NG 정확도, 노트북 메모리·속도, VLM 병행, 장시간 운영은 별도 검증 대상이다. 다음 개선은 정상 특징/기준 데이터의 GPU 유지 및 반복 전송 제거다.
