# 오류 처리와 재개

15단계는 오류 발생 시 검사·로봇 요청의 권한을 회수하고, 기록을 보존한 뒤 명시적인 확인을 거쳐 다시 시작하도록 한다. 운영 UI 상단에 미해결 오류, `오류 확인 · 재개 준비`, `진단 내보내기`를 추가했다. 아래 시간은 소프트웨어 감시 기준이며 실제 장비의 정지 시간이나 처리량 보장 수치가 아니다.

## 오류별 처리

| 상황 | 처리 | 재개 조건 |
|---|---|---|
| D405 연결 지연 | 15초 연결 제한, 별도 카메라 프로세스 종료 요청 | 장치 해제·원인 확인·오류 확인 후 재연결 |
| 영상 중단·SDK 무응답 | 새 영상 2초 부재 감지. 카메라 종료 요청 후 2초 내 응답이 없으면 해당 자식 프로세스 종료 | 이전 영상·판정 재사용 없이 새 카메라 회차 시작 |
| 동일 하드웨어 프레임 반복·번호/시간 역전 | 중복은 새 입력으로 세지 않으며 역전/잘못된 시간은 오류 | 카메라 재연결. 정지된 물체의 동일한 픽셀 영상 자체는 오류가 아님 |
| 모델 준비 멈춤 | 180초 감시 | 모델 해제 후 파일·GPU 상태 확인 |
| 검출·물체 검사 멈춤 | 진행 정보가 30초간 갱신되지 않으면 중단 | 원인 확인 후 모델을 다시 준비 |
| 정상 입력 대기 | 자식 프로세스가 진행 정보를 갱신하므로 입력이 없는 것만으로 모델 오류를 만들지 않음 | 새 영상과 사용자의 검사 시작 |
| 메모리 부족·검사 프로세스 비정상 종료 | 오류 분류·진단 기록, 현재 판정 무효화, 새 요청 차단 | GPU 점유·모델·메모리 상태 확인 후 재준비 |
| 검사 원본 저장 지연·권한·용량·DB 오류 | 저장 30초 감시. 저장/등록이 끝나기 전 결과를 공개하지 않음 | 공간·권한·DB 복구, 기본 저장 검사 통과 |
| 로봇 요청·통신·검증·기록 오류 | 정지 요청, 자동 재전송 금지, 대기 명령 폐기, 현재 작업 재개 금지 | 연결 해제·물체/장치 상태 확인·로봇 준비 확인·새 검사 |
| 로봇 작업자 상태 응답 부재 | UI가 5초간 상태 갱신 부재를 별도로 감지하여 운전 차단·정지 요청 | 실제 정지/물체 유지 상태와 통신 확인. 물리 상태를 추측해 재개하지 않음 |
| VLM 모델/작업자 오류 | 추가 분석 OFF. 기본 검사 판정 유지 | 원인 확인 후 상단 VLM 버튼으로 명시적 재요청 |
| 운전 중 VLM 기록 접근 오류 | 추가 분석 중단 및 별도 표시. 기본 검사/원본 DB가 정상이라면 기본 검사 유지 | VLM 기록 접근 복구 후 재요청 |

카메라 USB SDK 호출을 별도 프로세스에 격리해 드라이버 호출이 멈춰도 Qt 화면에서 종료를 진행할 수 있게 했다. 검사 프로세스도 종료 요청 후 응답이 없으면 폐기하며 살아 있는 이전 검사 프로세스가 있으면 새 모델을 준비하지 않는다. 종료된 프로세스의 잠금은 OS에서 해제된다.

로봇 직렬 통신은 읽기/쓰기 시간 제한을 사용한다. 정지 요청 시 큐에 들어 있던 집기·준비 확인 명령을 버리고 이미 꺼낸 요청도 세대 번호로 무효화한다. 계획 예약 후 운영 기록 저장이 실패하면 다음 동작 명령을 보내지 않는다. 통신 단절이나 물리 고장에서는 소프트웨어 정지 요청만으로 실제 정지를 확정할 수 없다. 실제 비상정지·안전 장치·정지/물체 유지 상태 확인은 현장 시험 대상이다.

## 오류 발생 시 화면

오류가 발생하면 먼저 검사 실행과 자동 분류를 끄고, 화면의 현재 판정을 무효화하며, 이전 세대의 늦은 결과를 거부한다. 모델 종료와 로봇 정지 요청을 보낸 뒤 오류를 기록한다. 기록 저장 자체가 실패해도 메모리에서 운전 차단을 유지한다. 기존의 저장된 검사 이력은 당시 근거로 남으며 현재 물체를 집는 근거로 재사용하지 않는다.

미해결 오류가 있을 때 `검사 시작`, 물체 집기, 자동 분류, 모델 준비를 차단한다. 단순한 검사 중단/재시작과 오류 복구는 다르다. VLM만의 모델 오류는 이 운전 차단을 만들지 않는다.

## 조치 순서

1. 원인을 확인한다. 필요하면 `진단 내보내기`로 다른 정상 저장 위치에 자료를 남긴다.
2. 모델을 해제하고 카메라·로봇 연결을 해제한다. VLM은 OFF로 둔다.
3. 저장 공간·권한·장치·물체·설치 상태를 확인하고 `오류 확인 · 재개 준비`를 누른다.
4. 확인자와 조치 내용을 기록한다. 이때 DB 간이 무결성, 실제 이벤트 쓰기, 최소 저장 여유를 확인한다.
5. 모델·장치를 다시 준비하고 로봇을 쓸 경우 로봇 준비 확인을 수행한다. **검사 시작은 별도로 누른다.**

버튼을 눌렀다는 사실이나 확인 메모만으로 실제 장비 상태가 검증되는 것은 아니다. 실패한 로봇 명령이나 과거 집기 계획을 재실행하지 않는다. 오류 확인 기록을 완료하지 못하면 운전 차단을 유지한다.

## 기록과 재시작

`operator-faults.json`은 검사 DB와 별도로 저장한다. 임시 파일 쓰기·파일 동기화·교체를 사용하며 같은 미해결 오류를 반복해서 쌓지 않는다. 최대 1,000건 범위에서 확인 완료한 오래된 기록을 정리하고 미해결 오류를 유지한다. 손상된 오류 파일은 조치 확인 시 원본 사본을 남긴 후 복구한다.

운영 DB에도 오류와 조치 이벤트를 남긴다. 독립 오류 파일 저장이 실패해도 DB에 미해결 오류가 남아 있으면 다음 시작에서 복구한다. 이전 검사 회차가 비정상 종료된 경우 자동 재개하지 않는다. 두 저장 경로 모두 쓰기 불가능하면 영구 기록 성공을 주장하지 않고 화면에 저장 실패를 표시한다.

진단 JSON에는 발생 오류, 최근 운영 이벤트 최대 200건, 장치/모델/VLM 상태, 검사 세대와 저장 위치를 포함한다. 기존 진단 파일을 덮어쓰지 않는다. 진단 자체가 실패하면 다른 정상 저장 위치를 선택한다.

앱 시작조차 불가능한 DB 손상은 원본을 임의로 삭제하거나 초기화하지 않는다. 별도의 새 운영 폴더로 실행하여 14단계의 검증된 백업을 새 폴더에 복원한다.

```powershell
.\.venv\Scripts\python.exe scripts\desktop.py --runtime C:\MES-Recovery\new-runtime
```

복원은 현재 폴더를 덮어쓰지 않으며 VLM OFF, 로봇 RECOVERY 상태로 시작한다. 새 위치·설치 조건·보정의 유효성을 확인한다. 백업 기능 범위는 [저장·백업 사용법](STORAGE.md)을 따른다.

## 검증 범위

실제 자식 프로세스에서 카메라 열기/읽기 무응답, 프로세스 종료, 추론 무응답, 메모리 예외를 주입했다. 저장 지연·등록 실패·오류 파일 손상·조치 기록 실패·정지 대기 명령 폐기·늦은 응답 차단·VLM 오류 격리도 검사한다. UI에는 이 주입 기능을 노출하지 않는다.

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe scripts\verify_recovery.py
```

`artifacts/recovery-check/all-tests.log`와 `report.json`, `ready.png`, `fault.png`, `recovered.png`를 확인한다. 실물 USB 탈착, 실제 로봇 정지/센서, GPU 실제 메모리 고갈, 저장 장치 고장·정전, 장시간 성능·RTX 5070 시험은 현장 및 후속 성능 검증에서 수행한다. 이 단계는 소프트웨어 장애 대응 검증이며 출고 승인 전체를 뜻하지 않는다.
