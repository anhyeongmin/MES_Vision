# 17단계 — 평가 도구와 현장 검증

설치 배포(16)는 실물 검사·노트북 성능·장치 연동 검증 후 진행한다. 이 단계는 재현 가능한 시험 도구와 소프트웨어 측정 결과를 준비한다. 실물 합격 기준을 임의로 통과시키지 않는다.

## 시험의 구분

| 시험 | 실행 도구 | 확인하는 것 | 확인할 수 없는 것 |
|---|---|---|---|
| 평가 계산·재생 회귀 | `tests/test_validation.py` | 전체 사진/라벨 대조, 오류/누락 보존, 원본 저장, 모델 재사용 | 실제 결함 정확도 |
| 연속 동작 | `scripts/verify_continuous.py` | 추적·중복 방지·선택 재검사·중단/재개·비동기 저장·DB | 카메라/로봇/실제 GPU 추론, 장기 무고장 |
| GPU 반복 부하 | `scripts/benchmark_inspection.py` | 실제 RF-DETR 2개+DINO, 거리 계산, 저장, 선택적 실제 Qwen 경합 | 합성 RGB에서 검출 정확도, 실제 작업 속도 보장 |
| 실물 사진 평가 | `scripts/evaluate_inspection.py` | 제품 모델·판정 기준으로 분리된 전체 사진을 검사하고 정답과 비교 | 실시간 추적 ID 정확도, 집기, 실제 단절 복구 |
| 현장 인수 시험 | `docs/FIELD_ACCEPTANCE.csv` | 설치 조건·품목·합격 기준·증거·승인 | 장비 없이 자동 완료할 수 없음 |

운영 화면의 검사 시작은 D405 실시간 입력을 계속 사용한다. 개발 시험은 별도 도구에서 실행하며, 재생 결과는 운영 이력에 등록하지 않고 로봇 명령을 생성하지 않는다.

## 실행 위치와 GPU 사용

프로젝트 루트에서 기존 `.venv` Python으로 실행한다. 모델을 해제하고 VLM을 OFF로 둔 상태에서 시작한다. 평가/벤치마크는 기본 운영 폴더의 GPU 상주 잠금과 우선 실행 잠금을 확보한다. 다른 품목의 상주 엔진이 있으면 시작을 거부한다. 별도 운영 폴더로 실행한 프로그램이나 다른 학습 프로그램은 이 잠금을 공유하지 않으므로 함께 실행하지 않는다.

```powershell
.\.venv\Scripts\python.exe scripts/verify_continuous.py --seconds 120 --output artifacts/performance-check/continuous-001
.\.venv\Scripts\python.exe scripts/benchmark_inspection.py --samples 30 --counts 1 4 8 --bank-size 2048 --vlm --output artifacts/performance-check/gpu-001
```

매 실행마다 새 출력 폴더를 지정한다. 기존 결과를 덮어쓰지 않는다. `--seconds`는 완결된 시나리오 단위로 종료하므로 실제 시간이 조금 더 길 수 있다. 연속 시험의 20 Hz는 제공 목표이며, 실제 처리된 프레임 수와 경과 시간을 함께 확인한다. 지연이 생기면 입력 간격이 늘어날 수 있는 단일 프로세스 계약 시험이다. 카메라 자식 프로세스·최신 프레임 큐의 동작은 기존 운영 회귀 시험으로 별도 확인한다.

GPU `--counts`는 검출된 물체 수가 아니라 **한 프레임에 검사할 원본 crop 수를 가정한 부하**다. 한 번 전체 검출 후 지정한 수만큼 결함 모델·DINO·정상 특징 거리 계산을 실행한다. 메모리는 고정 seed의 단위 길이 벡터로 만들며 실제 정상 등록 메모리가 아니다. 실물 모델/메모리 크기가 확정되면 다시 측정한다.

`VLM_OFF`, `VLM_LOADING`, `VLM_ON`을 구분한다. `VLM_ON`은 같은 작업의 분석 상태 안에서 시작·종료한 표본이다. 상태 전환에 걸친 표본도 `VLM_ON_BOUNDARY`로 원시 CSV/JSON에 보존하며 정상 구간 백분위에는 섞지 않는다. ON/OFF는 고정 입력의 반복 측정으로, 열·클록 변화까지 통제한 실험은 아니다. ON의 각 물체 수별 표본이 5개 미만이면 측정 불충분으로 실패 처리한다. 적은 표본의 p99는 안정적인 최악 시간 보장이 아니다.

VLM은 현재 상주 정책(전체 20 GiB 이상, 기본 모델 준비 후 여유 12 GiB 이상)을 만족할 때만 동시 실행한다. 조건 미달은 병행 측정 실패로 남기며 제품 운전에서는 VLM 대기 정책을 사용한다. VLM 완료·구조화 응답·참고 정보 표시·기본 검사 파일 불변을 검증한다. 실제 설명 내용의 옳고 그름은 별도의 실물 검토가 필요하다.

GPU 시간은 동기화 후 측정한다. `detect_ms`는 전체 물체 검출, `defect_ms/features_ms/distance_ms`는 해당 프레임의 모든 crop 합계, `save_ms`는 PNG와 측정 JSON 쓰기다. `total_ms`에 포함된 저장은 부하 시험용 파일 쓰기이며 운영 스냅샷 무결성 재검증·DB 등록·화면 표시와 같지 않다. OS 캐시 후 디스크 영구 저장 완료까지 보장하지 않는다. 카메라 촬영·추적 안정화 시간·Qt 표시·로봇 시간은 포함하지 않는다. 모델 초기 적재/검증/워밍업은 별도로 기록한다.

## 실물 준비 후 사진 평가

1. 확정된 카메라·조명·품목으로 수집 프로젝트를 만들고 실물 ID와 촬영 회차를 기록한다.
2. 학습/검증/시험 사이에서 같은 실물·회차·동일 픽셀이 섞이지 않게 분리한다. 정상과 알려진 NG는 `test`, 미등록 NG와 판독 불확실 사례는 `challenge`에 별도로 보존한다. 평가 대상 전체 사진을 검토 완료하고 빈 작업대도 명시적으로 확인한다.
3. 검증용 분할로 임계값을 정하고 제품/모델/정상 특징/품질 기준 버전을 고정한다. 시험·challenge 결과를 보고 기준을 수정했다면 그 자료는 이후 독립 인수 시험으로 재사용하지 않는다. 별도 수집 프로젝트나 외부 모델의 학습 자료까지 자동으로 누출 검증하는 것은 아니므로 학습 이력도 대조한다.
4. 저장된 품목 설정과 장비 설정 JSON을 준비하고 다음 명령을 실행한다. 품목 ID·모델 해시·품질 기준·해상도를 일치시킨다. 설정 파일은 운영 세션의 `product`/`equipment` 저장본을 각각 JSON으로 추출하거나 검증된 설정 백업에서 확보한다.

```powershell
.\.venv\Scripts\python.exe scripts/evaluate_inspection.py --collection data/my-product --product validation/product.json --equipment validation/equipment.json --output artifacts/performance-check/product-001
```

운영 세션을 이미 만들었다면 `--product`와 `--equipment` 대신 `--session-id 세션ID`를 사용할 수 있다. 해당 세션에 고정 저장된 두 설정을 읽기 전용으로 불러온다. 저장 폴더를 바꾸어 운전했다면 `--runtime 실제운영폴더`도 지정한다. 이 경로의 GPU 잠금을 공유하며, 평가 설정 복사본은 출력 폴더에 남긴다.

기본은 `test`와 `challenge` 두 분할이다. `--split test` 또는 `--split challenge`로 각각의 성능도 따로 산출한다. `--iou 0.5`가 기본이며 평가 전에 기준을 고정한다. 기존 challenge 내보내기는 물체별 crop이므로 전체 장면 검출 평가에 사용하지 않는다. 이 도구는 수집 프로젝트의 전체 사진을 직접 읽는다.

`report.json`, `objects.csv`, `predictions.json`, `truth.json`, 설정/수집/판정 기준 복사본, `snapshots`를 남긴다. 모델은 한 번 적재하고 모든 사진에 재사용한다. 입력 해시가 다르면 중단하거나 해당 프레임을 오류로 기록한다. 해상도를 임의 변경하지 않는다. 파일 재생에는 실시간 안정화 대기와 추적 ID가 없으므로 모든 사진의 모든 검출 물체를 검사한다. 품질/작업 영역 조건이 나쁘면 보류 사유를 유지한다. 작업 영역 밖 정답도 분모에 남겨 잘못된 ROI가 누락을 숨기지 못하게 한다.

### 결과 읽기

- 상자는 IoU 기준으로 일대일 연결한다. 가능한 연결 수를 최대화한 뒤 IoU 합을 비교한다. 중복 검출은 추가 검출로 집계한다.
- `MISSED`: 처리는 성공했으나 해당 정답 물체를 검출하지 못함. `ERROR`: 프레임 처리 실패로 평가하지 못함. 둘 다 전체 대상 검출 재현율의 분모에서 빠지지 않는다.
- `ng_passed_as_ok`: 알려진/미등록 불량 중 OK 판정된 비율. 이 수치가 낮아도 누락·오류·보류가 많으면 합격이 아니다.
- `normal_rejected_as_ng`: 정상 중 NG 비율. 정상 보류는 별도로 혼동표에서 확인한다.
- `UNKNOWN_NG`와 `UNCERTAIN`은 정상과 합치지 않는다. 미등록 NG가 특정 불량 코드로 NG 처리된 경우와 `NG_UNKNOWN` 처리된 경우는 개별 행의 코드로 구분할 수 있다.
- 복수 불량 코드는 각각의 재현율을 산출한다. 결함 위치 mAP나 이유 설명 정확도까지 검증한 수치는 아니다.
- 분모 0은 `null`이다. 0% 오류나 100% 정확도로 바꾸지 않는다. 단위는 사진 속 물체 출현 횟수이므로 같은 실물의 반복 사진은 독립 표본이 아니다.
- 프레임 시간에는 파일 읽기·검사·원본 저장이 포함된다. 초기 모델 준비 시간은 별도다. 실패한 프레임의 시간도 제외하지 않는다.

`acceptance=NOT_ASSESSED`는 의도적이다. 표본 수·물체 수·최소 결함 크기·허용 누락/오판·p95 응답 시간·연속 시간·집기 성공 조건을 사용자와 정한 뒤 현장 시험표에 근거를 연결해 승인한다.
